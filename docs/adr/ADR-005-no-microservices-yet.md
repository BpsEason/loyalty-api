# ADR-005: Why No Microservices Yet

## Context

在系統架構設計的討論中，是否要一開始就採用微服務架構是一個常見的話題。本系統目前所有的業務域都運行在同一個應用程式中，共享同一個資料庫和部署流水線。

核心業務域：

- Authentication（身份驗證）
- Multi-Tenancy（多租戶）
- Customer（客戶管理）
- Point Account（點數帳戶）
- Point Transaction（點數交易）
- Campaign（行銷活動）
- Reward（獎勵管理）
- Admin Panel（管理後台）

這些域之間仍然存在緊密的業務關聯和事務邊界重疊。

## Decision

**系統在當前規模下故意不使用微服務架構，維持 Modular Monolith（模組化單體架構）。**

這不是因為微服務本身不好，而是因為在當前階段，分散式系統的複雜性超過了它帶來的好處。我們遵循的決策流程是：

```text
Measure
   ↓
Identify Bottleneck
   ↓
Benchmark
   ↓
Optimize
   ↓
Re-measure
   ↓
Architectural Change
```

而不是常見的反模式：

```text
More Users
   ↓
Microservices
```

## Why Microservices Are Not Needed Today

### 1. 事務邊界仍然重疊

- 點數交易需要同時訪問 Customer、PointAccount、PointTransaction 等多個域的數據
- 獎勵發放需要跨 Campaign、RewardGrant、PointTransaction 等模組的一致性保證
- 分散式事務（如 Saga、2PC）的複雜性遠超過當前系統的需求
- 單體架構下的 ACID 事務可以簡單可靠地解決這些一致性問題

### 2. 共享資料庫目前足夠

- 單一 MySQL 資料庫可以輕鬆支撐當前甚至未來一段時間的數據量和並發量
- 數據庫層的分片或拆分還遠未到來
- 聯合查詢、事務都可以簡單實現，不需要跨服務 API 調用

### 3. 操作複雜性不划算

- 微服務需要獨立的部署流水線、監控、日誌收集、鏈路追蹤
- 需要服務發現、負載均衡、熔斷機制等分布式系統基礎設施
- 開發者需要處理網絡失敗、超時重試、冪等性等一系列分佈式系統問題
- 團隊規模和運維能力還不需要這些複雜性

### 4. 當前瓶頸需要先被測量

- 在沒有實際測量到性能瓶頸之前就進行架構拆分是過度設計
- 單體應用的性能問題通常可以通過優化查詢、添加索引、緩存等方式解決
- 只有當確定某個業務域確實需要獨立擴展時，拆分才有意義

## Alternatives Considered

### 1. Modular Monolith（目前選擇）

- **優點**:
    - 事務邊界簡單，ACID 保證容易
    - 部署簡單，一個應用包搞定
    - 開發速度快，調試容易
    - 域之間的調用是本地函數調用，沒有網絡開銷
    - 運維複雜度低，不需要分佈式系統基礎設施
    - 仍然可以保持模組之間的清晰邊界

- **缺點**:
    - 應用擴展只能整體擴展，不能針對熱點模組單獨擴展
    - 隨著時間推移，模組之間可能出現耦合
    - 技術棧統一，無法為不同模組選擇最合適的技術
    - 未來提取模組成微服務需要明確的邊界定義

### 2. Microservices Immediately

- **優點**:
    - 每個服務可以獨立擴展
    - 技術棧靈活，不同服務可以使用不同語言/框架
    - 故障隔離，一個服務掛掉不影響其他服務
    - 團隊可以獨立開發和部署各自的服務

- **缺點**:
    - 分散式事務的複雜性，需要處理數據一致性問題
    - 網絡失敗、延遲、超時等分佈式系統的經典問題
    - 服務發現、配置管理、監控日誌等基礎設施成本高
    - 部署複雜，需要管理多個運行中的服務實例
    - 開發者門檻高，需要理解分佈式系統的各種陷阱
    - 在當前系統規模下，這些成本遠超過收益

## Consequences

### 正面影響

- 專注於業務邏輯實現，而不是分佈式系統的編程
- 開發速度快，功能交付週期短
- 操作簡單，部署和維護成本低
- 事務一致性保證簡單可靠
- 調試和問題排查容易

### 風險與挑戰

- 需要保持模組之間的清晰邊界，避免演變為大泥球
- 需要持續關注系統性能，及時識別瓶頸
- 在合適的時機需要有能力提取出獨立的服務
- 代碼庫隨著時間可能變得很大，需要良好的模組化設計

## Exit Criteria

當以下任何一個條件滿足時，重新評估微服務架構：

### 明確的擴展瓶頸出現

- 某個業務域的負載遠遠超過其他模組，需要單獨擴展
- 數據庫層出現無法通過優化解決的性能瓶頸
- 某個模組的資源消耗嚴重影響其他模組的運行

### 不同域有完全不同的擴展特性

- 某些模組需要處理極高的並發（如點數交易）
- 某些模組需要大算力（如數據分析、報表生成）
- 這些模組的資源需求完全不同，無法在同一個實例中協調

### 部署獨立性成為真實需求

- 不同的業務團隊需要獨立部署自己的模組
- 某些功能需要頻繁發布，而核心系統需要穩定
- 獨立部署可以降低發布風險，提高迭代速度

### 團隊所有權邊界出現

- 團隊按照業務域拆分，每個團隊負責一個完整的業務域
- 團隊之間需要獨立的開發流程和部署周期
- 服務邊界成為團隊之間的接口契約

## 未來的提取路徑

當需要拆分時，我們已經為此做好了準備：

- 所有業務邏輯都封裝在 Service 層，有清晰的 API 邊界
- 資料庫的關聯已經設計得相對獨立
- API 閘道器的模式已經存在，可以平滑過渡到微服務的 API 閘道
- 先提取出最獨立的模組，逐步遷移，而不是一次性全部拆分

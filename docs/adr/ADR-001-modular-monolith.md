# ADR-001: Modular Monolith

## Context

目前系統包含以下核心領域模組：

- Authentication (身分驗證)
- Multi-Tenant (多租戶管理)
- Customer (客戶管理)
- Point Account (點數帳戶)
- Point Transaction (點數交易)
- Campaign (行銷活動)
- Reward (獎勵管理)
- Coupon (優惠券管理)
- Admin Panel (管理後台)

這些領域仍然共享：

- 單一資料庫 (Shared Database)
- 單一部署流程 (Shared Deployment)
- 統一的身份驗證機制
- 交易邊界高度重疊（例如點數交易需要同時操作 PointAccount 和 PointTransaction）

因此，目前階段採用 Modular Monolith 架構是最合適的選擇。

## Decision

採用 **Laravel Modular Monolith** 架構，而不是一開始就拆分為 Microservices。

系統透過 Laravel 的目錄結構來維持領域分離：

- `app/Services/Point/` - 點數交易核心邏輯
- `app/Services/Reward/` - 獎勵服務邏輯
- `app/Support/Tenancy/` - 租戶相關支援類別
- 模型、控制器、中介軟體按功能組織，但仍在同一應用程式中

## Alternatives Considered

### 1. Modular Monolith (採用)

- **優點**:
    - 交易邊界簡單，ACID 保證容易實現
    - 開發速度快，不需要處理分佈式系統複雜性
    - 部署簡單，單一部署單元
    - 領域分離仍然可以透過目錄結構和程式設計規範實現
    - 除錯和觀測性相對簡單

- **缺點**:
    - 應用程式擴展無法完全隔離，某個模組的流量高峰可能影響整個系統
    - 大型模組可能產生緊密耦合的風險
    - 未來提取獨立服務需要明確的邊界定義

### 2. Microservices (未採用)

- **優點**:
    - 獨立部署和擴展
    - 團隊所有權邊界清晰
    - 技術棧選擇靈活

- **缺點（這些成本目前無法承擔）**:
    - 分佈式事務复杂性：需要處理跨服務數據一致性
    - 網絡故障風險：服務間通信可能失敗
    - 服務發現需求：需要額外的基礎設施來管理服務位置
    - 部署複雜性指數增長
    - 觀測性成本高，需要分散式日誌、追蹤系統
    - 數據一致性難以保證
    - 運維開銷顯著增加
    - 對於目前的團隊規模和業務規模，這些複雜性是過度設計

## Consequences

### 正面影響

- 交易邊界保持簡單，點數交易等核心操作可以輕鬆使用資料庫事務保證一致性
- 開發效率高，新功能可以快速上線
- 部署流程簡單，減少運維負擔
- 透過目錄結構和程式設計規範，仍然可以實現良好的領域分離

### 負面風險

- 應用程式層級的擴展隔離性較差，無法針對高流量模組單獨擴展
- 如果不維護好程式邊界，大型模組可能變得緊密耦合
- 未來如果需要拆分微服務，需要進行額外的重構工作

## Exit Criteria

當以下任一條件滿足時，將重新評估 Microservices 架構：

1. 出現明確的可擴展性瓶頸，且無法透過優化或垂直擴展解決
2. 不同領域展現出完全不同的擴展特性（例如點數交易需要比後台管理多10倍的資源）
3. 獨立部署成為實際業務需求，不同團隊需要獨立發布各自的模組
4. 團隊規模增長到需要按領域劃分獨立的小團隊，團隊所有權邊界成為實際需求
5. 業務發展證明某些模組需要獨立的技術棧或部署策略

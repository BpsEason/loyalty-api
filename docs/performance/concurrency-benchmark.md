## 業務不變量驗證

在沒有其他並發 earn/refund 操作的場景中，以下等式必須始終成立：

```
成功兌換總額 + 最終餘額 = 初始餘額
```

## 觀察到的保護機制

目前實現的並發控制機制：

1. Redis 分佈式鎖（防止跨進程並發）
2. MySQL 行鎖 (`lockForUpdate()`)，保證同一數據庫連接內的串行化
3. 資料庫層級的餘額檢查 (`WHERE balance >= amount`) 作為最後一道防線
4. 死鎖重試機制（3 次重試）
5. 數據庫級冪等性，防止重複處理同一請求

## 已知限制

- Redis 依賴：分佈式鎖依賴 Redis 的可用性
- 單數據庫寫入：所有點數變更都需要對 PointAccount 行加鎖，存在寫入瓶頸
- FIFO 鎖順序：先鎖帳戶，再鎖批次，避免死鎖

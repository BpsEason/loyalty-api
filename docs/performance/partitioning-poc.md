# 數據庫分區可行性分析

> 最後更新：2026-09-20

## 目前狀態分析

### 當前交易數量

- 狀態：尚未達到分區門檻
- 實際數據量：待收集
- 建議分區閾值：單表數據量 > 1000 萬筆

## 分區關鍵字分析

### 候選分區鍵

1. `tenant_id` + `created_at`（複合鍵）
2. 僅 `created_at`（時間範圍分區）
3. 僅 `tenant_id`（列表分區）

## 分區場景分析

### 若實現 `tenant_id` + `created_at` 範圍分區

#### 受益的查詢

- 查詢某租戶最近一個月的交易記錄

    ```sql
    SELECT * FROM point_transactions
    WHERE tenant_id = ? AND created_at BETWEEN '2026-09-01' AND '2026-09-30'
    ```

    可利用分區剪枝，只掃描相關分區。

- 查詢某客戶最近的交易記錄
    ```sql
    SELECT * FROM point_transactions
    WHERE customer_id = ? AND tenant_id = ? ORDER BY created_at DESC LIMIT 10
    ```

#### 受影響的查詢

- 全域統計查詢（跨多個分區）
- 跨租戶報表分析

## 運營成本

### 分區帶來的好處

- 大數據量下的查詢性能提升
- 歷史數據歸檔更簡單（直接卸載分區）
- 熱點數據與冷數據物理隔離

### 分區帶來的運營複雜度

- 備份還原複雜度提高
- 跨分區事務開銷
- 遷移過程的停機風險
- 維護成本增加，需要定期創建新分區

## 結論

目前不需要實施分區，建議當單表數據量接近 500 萬筆時重新評估。
當前的數據庫索引設計已能支持當前業務量。
